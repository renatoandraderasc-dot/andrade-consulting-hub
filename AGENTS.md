Mercadológicos devem ser lidos pelas funções compartilhadas de `src/lib/mercadologico.ts`, pois os conectores usam aliases diferentes para os mesmos níveis.
PIC TV validates the login-selected store through store access rules and ignores URL/display overrides; this prevents unintended cross-store display.
PIC TV weather uses browser-authorized location with Open-Meteo and degrades independently; store location is not guessed from its name.
- TV signage (tv_telas/tv_itens + private bucket tv-midia) is managed by global admins, or by users with an explicit allowed admin_tv module row limited to their approved stores (tv_pode_gerir); players at /tv/:id read through store-access RLS and are the only screens besides PIC TV allowed to auto-refresh.
- TV dimensions are per physical screen; grid counts derive total dimensions through tvDimensoes. The player splits the viewport into one cell per physical module and assigns active items round-robin by order (item i → module i % modules), each module rotating independently, so square artwork fits each module without stretching. Unknown resolution remains null to avoid inventing hardware specifications.
- Stores with store_vr_config.max_dias_consulta are read one month at a time (dre_periodo monthly, kept forever in relatorio_cache; only current/previous month renewed by sync-diario-d1); vr-proxy has per-report day-limit exceptions — slow bridges crash on long or parallel queries.
- Lancamentos pass through DB trigger fn_normalizar_lancamento (non-manual rows only): maps raw ERP account names to official DRE accounts and applies per-store supplier rules, so every import path stays consistent.
- Escala generation and validation must import the supplied src/lib/escala/escala-motor.ts unchanged; database loading, persistence and UI are separate modules so integration does not alter the supplied scheduling rules.
- Escala generated allocations are persisted atomically by escala_salvar_geracao in batches of 500 with explicit authenticated store-management and payload ownership checks before privileged writes and a period lock, avoiding repeated row-level access checks while preserving locked cells; this function only persists browser-generated data and never generates or certifies legal compliance.
- User editing loads all permission pages and submits only changed access fields; module changes use a single upsert without deleting existing rows, preventing truncated reads and unrelated profile edits from erasing permissions.
- TV price artwork uses a single full-height grid whose rows own their alternating stripe, product and price; this prevents independently positioned backgrounds from crossing product labels.
- Every client page renders inside ClientLayout, which mounts the floating PrintTelaButton (PNG capture of the main area); new screens get it automatically by using ClientLayout.
- Comparativo de Departamentos e Produtos reads ranking_produtos one month at a time and stores closed months as compact rows in painel_periodo_cache (relatorio comparativo_produtos_v1); the store-wide receipt count comes from cupons_e_ticket because summing per-department receipts would double count.
- All report readers prefer the newest complete matching Hub snapshot over secondary caches; row-limit variants are equivalent only when not truncated. Comparativo auto-loads saved data only, keeping ERP refresh explicit and guarding asynchronous store/filter changes.
- Dashboard daily realized sales use vendas_secao_dia for DIRECTOR via consultarVendasDiarias, with sequential per-day fallback for undated responses; period totals must not be assigned to the first day.
- Purchase target generation preserves aggregated LOJA/GERAL rows and the established loss/recovery formula; financial totals sum only department rows to avoid double counting buyer targets.
- Purchase realized views use the union of report movements, full catalog departments and configured departments; goal activation flags and recent product activity never filter realized amounts, preserving complete ERP totals.
- Calendar campaign blocks have stable component identity, so asynchronous saves do not reset another block's focus or draft.
- Fixed-format prize image exports pass measured layout width and height to the image renderer; clone styles alone do not set canvas dimensions.
- Dynamic stock fallback groups product rankings by verified last-entry dates through D-1, queries sequentially, and rejects incomplete results; first-purchase dates are never treated as last entries.
- Heavy movement reports (including purchase entries) are fetched sequentially by day and retained in relatorio_cache; shared hubDados merges only additive movements and preserves separate invoice entries, preventing gateway timeouts and incorrect unit-cost sums.
- Store synchronization uses persisted store_sync_jobs queues with per-store uniqueness and worker leases; only authenticated approved-store access or trusted cron credentials can start/resume work, and Conexões polls saved progress only after an explicit request, keeping ERP refresh manual and resumable.
- NF-e receipt validation and WebSac entry are separate edge functions using _shared/consultaLoja.ts; preserve the supplied workflow so validation stays separate from ERP writes.

- Receipt screens use cached manual-refresh reads and explicit header columns; blind counting unmounts invoice views, evicts invoice detail caches, and queries only safe criterion fields so invoice quantities are not passed into counting.
- Receipt business writes invoke the published functions; only own blind counts and global-admin configuration write directly, preserving existing RLS.
- The public presentation uses isolated illustrative screens and a single 1920×1080 slide master; partner logos and replacement media stay in browser IndexedDB, so shared presentation links never expose store data or silently publish uploaded files.
- Presentation media pointers are imported as raw text and parsed defensively; an incomplete upload must fall back to an illustrative screen instead of failing Vite JSON transformation and blanking every route.
- Demo membership is read from protected demo_workspaces and never grants an admin role; ModuleGuard mounts only isolated domain views, whose mutations serialize to the owner's JSON workspace, while restrictive RLS denies demo accounts access to production tables. New production tables must also carry the demo_production_isolation policy to preserve this boundary.
